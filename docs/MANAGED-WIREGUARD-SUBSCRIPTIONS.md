# Управляемая подписка WireGuard для Pushok Flow

## Назначение и ответственность проектов

Контракт `pushok-flow-subscription` версии 1 связывает клиент Flow с существующим
сервером Shop и отдельным узлом WGDashboard. Flow получает персональную
HTTPS-ссылку устройства, сохраняет проверенные профили и подключается к
WireGuard-серверу после действия пользователя. Административный API WGDashboard
вызывает только Shop. Этот контракт описывает клиентский этап v0.57.0;
совместимая выдача Shop и приёмка настоящего узла выполняются отдельно.

| Проект | Работа | Условие готовности |
| --- | --- | --- |
| WGDashboard | Отдельный сервер с обычным WireGuard, интерфейс, резервное копирование и закрытый API | Конфигурация тестового устройства передаёт трафик; отзыв реально закрывает доступ и сохраняется после перезапуска |
| Shop | Переиспользовать адаптер WGDashboard; выдавать feed устройства, состояния и возрастающие ревизии | Проверены выдача, обновление, продление, истечение, восстановление и отзыв; экспорт разрешён только соответствующему устройству |
| Flow | Разбирать v1, сохранять каталог атомарно, показывать состояние, проверять срок до нового подключения | Проверки parser, каталога, шифрованного хранения и интерфейса; затем приёмка на телефоне |
| Pushok ID | Будущая общая идентичность и связывание действующих аккаунтов | Отдельно согласованы и развёрнуты сервис входа, домен и разрешения; приложение не использует административные сессии |
| SOO Pushok и `@pushok_app` | Общая навигация и последовательность подключения сервисов | Пользователь получает доступ к своему устройству и понятный путь продления без повторной регистрации |

Текущий аккаунт Flow продолжает читать только профиль и баланс MTProxy.
Его сессия не является разрешением Shop на выдачу конфигураций. Изменения
MTProxy и внедрение нового входа не входят в этот клиентский этап.

## Ответ HTTPS

Сервер возвращает UTF-8 JSON, предпочтительно с `Content-Type: application/json`
и `Cache-Control: no-store`. Весь ответ ограничен 512 КиБ. Заголовки
`Subscription-Userinfo` и `Profile-Title` не заменяют поля управляемого ответа.
Название самой подписки выбирается в форме Flow.

Пример с искусственными ключами и адресом для документации:

```json
{
  "schema": "pushok-flow-subscription",
  "version": 1,
  "revision": 1,
  "state": "active",
  "expires_at": 4102444800,
  "profiles": [
    {
      "id": "device_01_node_01",
      "name": "Основной сервер",
      "protocol": "wireguard",
      "config": "[Interface]\nPrivateKey = AQEBAQEBAQEBAQEBAQEBAQEBAQEBAQEBAQEBAQEBAQE=\nAddress = 10.77.0.2/32\nDNS = 1.1.1.1\n[Peer]\nPublicKey = AgICAgICAgICAgICAgICAgICAgICAgICAgICAgICAgI=\nEndpoint = 203.0.113.10:51820\nAllowedIPs = 0.0.0.0/0, ::/0\nPersistentKeepalive = 25\n"
    }
  ]
}
```

| Поле | Правило v1 |
| --- | --- |
| `schema` | Строка `pushok-flow-subscription` |
| `version` | Целое число `1` |
| `revision` | Целое число от 1 до 9007199254740991; увеличивается при изменении состояния, срока или списка профилей |
| `state` | Только `active`, `expired` или `revoked` |
| `expires_at` | Обязательные целые Unix-секунды UTC от 1 до 253402300799; не миллисекунды и не строка даты |
| `profiles` | Для `active` от 1 до 20 записей; для `expired` и `revoked` ровно пустой массив |
| `profiles[].id` | Стабильный идентификатор профиля внутри этой подписки, 1–64 символа `A–Z`, `a–z`, `0–9`, `_`, `-` |
| `profiles[].name` | Непустое название после нормализации, до 64 Unicode-символов, без управляющих символов |
| `profiles[].protocol` | Только строка `wireguard` |
| `profiles[].config` | Полная клиентская конфигурация обычного WireGuard, до 65536 символов и в пределах общего ограничения ответа |

Все перечисленные поля обязательны; неизвестные и повторяющиеся ключи JSON
отклоняются. Строковые числа, дроби, комментарии JSON, данные после объекта и
неправильная кодировка также отклоняются. Повтор идентификатора или одинаковых
эффективных настроек подключения внутри подписки недопустим.

В конфигурации требуется одна секция Interface с закрытым ключом и адресом,
один Peer с открытым ключом, Endpoint с портом и AllowedIPs. Конфигурация проходит
настоящий parser WireGuard до изменения каталога. Скрипты `PreUp`/`PostUp`,
параметры AmneziaWG и настройки исключений приложений из ответа провайдера
не поддерживаются. Исключения приложений задаёт сам пользователь Flow.

Это узкий формат v1. Обычный JSON другой панели, `wireguard://`, Base64-обёртка
этого JSON и HTTPS-ответ с одним `.conf` не становятся подпиской автоматически.
Обычный импорт отдельного `.conf` или QR остаётся доступен.

## Ревизии и выбранный профиль

`id` профиля относится только к одной подписке. Одинаковый `id` в двух
подписках не объединяет их. При обновлении Flow сохраняет локальный UUID и
выбор сервера по этому идентификатору, даже если меняются имя, Endpoint или
ключи. После изменения конфигурации старый загруженный экземпляр не может
быть использован для подключения: проверяются и UUID, и точный текст.

Ревизия ниже уже сохранённой отклоняется. Повтор той же ревизии разрешён
только с прежними состоянием, сроком и точным упорядоченным списком
идентификаторов, имён и конфигураций. Такой повтор обновляет время успешной
проверки. Для любого изменения сервер увеличивает ревизию, включая
восстановление после `expired` или `revoked`.

Формат уже добавленной подписки не меняется при обновлении. Управляемый
endpoint не может перейти на обычный VLESS-список и обойти правила состояния
или ревизии. Для осознанной смены формата подписку добавляют заново.

## Истечение и отзыв

Пример явного отзыва:

```json
{
  "schema": "pushok-flow-subscription",
  "version": 1,
  "revision": 2,
  "state": "revoked",
  "expires_at": 4102444800,
  "profiles": []
}
```

Проверенный `expired` или `revoked` атомарно удаляет только профили этой
подписки. Сама подписка остаётся: в карточке видны состояние и действия
обновления/удаления. Ручные профили и другие подписки сохраняются.
Если удалён выбранный профиль, выбирается оставшийся либо выбор становится
пустым. Соединение автоматически не включается.

`active` с прошедшим `expires_at` допустим как сохранённый ответ, но Flow
показывает истёкший срок и отказывает в загрузке для подключения, выборе и
финальной проверке перед запуском туннеля. Последняя проверка выполняется
после подтверждения Android, поэтому истечение во время системного диалога
тоже учитывается. Локальные часы не заменяют серверную авторизацию.

В v0.57.0 уже работающий туннель не отключается таймером подписки. Обновление
каталога сохраняет существующее требование: собственный туннель Flow должен
быть выключен. Реальное истечение и отзыв обеспечивает Shop через удаление
или ограничение peer на WGDashboard, в том числе для ранее скопированного
`.conf`. Отключение ссылки скачивания само по себе не запрещает WireGuard-трафик.

Ошибка HTTPS, HTTP 401/403/410, неправильный JSON, пустой обычный VLESS-ответ
или ошибка записи не превращаются в подтверждённый отзыв. При отказе
проверки прежний каталог сохраняется. Просроченный управляемый профиль при
этом остаётся заблокирован для нового подключения по своему сохранённому сроку.

## Хранение и совместимость

Ссылка устройства, конфигурации, provider ID и revision остаются в нативном
зашифрованном каталоге. В общие метаданные списка подписок для Flutter
добавлены только `format` / `state`. Эти метаданные не содержат закрытых ключей, полного URL и
идентификатора устройства провайдера. Ошибки и диагностический текст используют
фиксированные коды.

Запись каталога получает схему 3 с прежним ключом Android Keystore и прежним
AAD. Старые схемы 1 и 2 читаются как ручные профили и обычные подписки.
Новый номер схемы не позволяет старому APK молча прочитать ограничения
WireGuard как обычный список. Смена сертификата или ключа шифрования не нужна.

Plaintext/Base64-подписки VLESS сохраняют прежнее поведение. Срок из их
`Subscription-Userinfo` остаётся информационным. Общие лимиты — пять подписок
и двадцать профилей. HTTPS, проверка сертификата и публичных DNS/IP,
ограничение перенаправлений и запрет административных заголовков сохраняются.

## Последовательность внедрения

1. Зафиксировать этот контракт в Flow и реализовать клиентскую обработку
   вместе с тестами на старые форматы и новое состояние.
2. В Shop добавить экспорт v1 и переход в Flow для WireGuard. На каждое
   логическое устройство создавать отдельные peer/ключи и персональную ссылку.
   При обычном продлении сохранять peer и ключ, увеличивать revision и срок.
3. На отдельном WGDashboard проверить полный путь одного устройства:
   выдача, импорт, подключение, передача трафика, продление, истечение,
   восстановление, отзыв, перезапуск узла. Затем расширять число устройств
   и локаций.
4. Подключить Pushok ID и общий интерфейс SOO отдельным контрактом, когда
   готовы сервис и домен. Первый сценарий с персональной ссылкой от этого
   этапа не зависит.

Первый серверный вариант переиспользует шифрованное хранение ключей Shop.
Генерация закрытого ключа непосредственно в Flow потребует отдельного
обмена только открытым ключом и сборки клиентского конфига на устройстве.
Она не включена в v1.
