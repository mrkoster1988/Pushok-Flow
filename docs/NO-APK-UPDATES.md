# Обновления данных без установки APK

Дата решения: 22.11.2026. Пользователь просит получать изменения без повторных установок и выпускать APK только при необходимости.

## Два независимых канала

Обычный APK обновляет установленный `shop.pushok.flow` с прежним постоянным сертификатом. Удаление приложения не является шагом обновления. Нативный обновлятор не вызывает удаление; перед открытием системного установщика он проверяет пакет, более высокий номер сборки, размер, SHA-256 и сертификат. Реальное сохранение профилей и настроек при обновлении на физическом телефоне ещё требуется проверить.

Отдельный канал рекомендаций обновляет только данные внутри приложения. Он не открывает установщик Android, не загружает исполняемый код и не меняет номер версии приложения. Механизм впервые добавлен в [опубликованный APK v0.34.0](https://github.com/mrkoster1988/Pushok-Flow/releases/tag/v0.34.0); уже установленная v0.33.0 сама получить этот новый механизм не может.

| Изменение | Способ доставки |
| --- | --- |
| Список рекомендуемых приложений для прямого подключения | Подписанные данные, без APK |
| Выбор исключений, импорт и редактирование профиля | Обычные действия внутри приложения |
| Логика экранов Flutter, обработка ошибок, новые функции | APK с прежним сертификатом |
| WireGuard, Kotlin, разрешения, нативные библиотеки | APK с прежним сертификатом |

Flutter hot reload предназначен для разработки, а не обновления установленного release-приложения: [режимы сборки Flutter](https://docs.flutter.dev/testing/build-modes). Отдельные системы доставки Dart-патчей, например [Shorebird](https://docs.shorebird.dev/flutter-concepts/plugins-and-native-code/), требуют своего runtime и инфраструктуры; в Pushok Flow они не подключены. Список рекомендаций не выдаётся за замену такому механизму.

## Пользовательский сценарий

В «Маршрутах» есть отдельная карточка рекомендаций. Она читает последний проверенный список из локального хранилища. Кнопка **«Обновить рекомендации»** запускает сетевую проверку; открытие экрана и возврат из фона сами сетевой запрос не запускают. **«Рекомендованные»** показывает только совпадения с приложениями, которые Android вернул в локальном списке. Названия берутся с телефона.

Версия и список сохраняются между запусками. Время успешной сетевой проверки относится к текущему процессу приложения: после полного перезапуска оно появится при следующей проверке. Чтение кэша не выдаётся за свежий ответ сервера.

Рекомендация не означает, что приложение обязательно требует прямого маршрута. Решение принимает пользователь обычным переключателем. Обновление списка не отмечает новые приложения, не снимает прежние исключения, не меняет профиль и не переподключает туннель. Удаление пакета из рекомендаций не удаляет пользовательский выбор.

Недоступный интернет, неверная подпись или устаревший ответ сохраняют последнюю принятую версию рекомендаций. Ошибка этого канала не блокирует поиск, просмотр и редактирование локальных исключений. До первой успешной загрузки доступен пустой список рекомендаций, а полный локальный список работает как раньше.

## Публичный формат

Источник человекочитаемых данных: [config/route_recommendations.json](../config/route_recommendations.json). Схема: [config/routing_rules.schema.json](../config/routing_rules.schema.json).

```json
{
  "schema_version": 1,
  "rules_version": 1,
  "recommended_bypass_packages": ["com.example.app"]
}
```

Пример выше иллюстрирует формат, а не реальное приложение. Принимаются только три заданных поля: схема `1`, целый положительный номер данных до `2147483647` и не более 256 уникальных идентификаторов пакетов длиной до 255 символов. Версия `0` зарезервирована для локального пустого состояния. Сценарии, адреса серверов, конфигурации туннеля, подписи интерфейса и ссылки в формате отсутствуют.

Публичный файл [updates/route-recommendations.json](../updates/route-recommendations.json) содержит конверт из трёх полей:

```json
{
  "schema_version": 1,
  "payload": "BASE64_EXACT_UTF8_PAYLOAD",
  "signature": "BASE64_RSA_SIGNATURE"
}
```

Это пример структуры, не действительная подпись. Подписываются точные декодированные байты payload с префиксом UTF-8 `Pushok Flow route recommendations v1\n`. Алгоритм — `SHA256withRSA`. Используется существующий постоянный ключ выпуска; отдельная подпись данных не меняет подпись Android-приложения. Проверка на телефоне использует открытый ключ единственного текущего сертификата установленного APK.

Для автономной проверки в репозитории хранится только [открытый сертификат](../config/route-recommendations-certificate.pem). Его SHA-256: `8b4114881116a920c3351b503052ac27078fdbbfcae1ace27f1af8245ebb7047`. Закрытого ключа и паролей в репозитории и CI нет.

## Проверка и сохранение

Нативный клиент обращается только к `https://raw.githubusercontent.com/mrkoster1988/Pushok-Flow/main/updates/route-recommendations.json`. Он не добавляет параметры запроса и не передаёт список установленных приложений, профиль, ключи или локальные оценки. Как при обычном HTTPS-запросе, сервер доставки видит сетевое подключение клиента.

Конверт ограничен 131072 байтами, payload — 65536 байтами, подпись — 256–1024 байтами. Проверяются подпись, поддерживаемая схема, строгие типы, состав полей, уникальность и синтаксис пакетов. Старая версия отвергается; повтор той же версии допустим только при идентичных байтах payload. Исправление опубликованных данных выпускается с новым `rules_version`, включая возврат к прежнему списку.

Кэш хранится атомарно в приватных файлах приложения и повторно проверяется при чтении. Новые данные становятся текущими только после успешной записи. Действия выполняются в отдельной последовательной очереди и отделены от хранилищ профилей, пользовательских исключений и состояния WireGuard.

## Выпуск следующей версии данных

1. Проверить точные идентификаторы по первичному источнику и описать причину изменения. Увеличить `rules_version` в `config/route_recommendations.json`.
2. Подписать данные локально сохранённым постоянным ключом. Инструмент читает путь к хранилищу, alias и пароли только из переменных `FLOW_DATA_KEYSTORE`, `FLOW_DATA_KEY_ALIAS`, `FLOW_DATA_STORE_PASSWORD`, `FLOW_DATA_KEY_PASSWORD`; секреты не передаются аргументами и не выводятся.
3. Проверить конверт открытым сертификатом и соответствие исходному JSON, затем опубликовать оба файла одним коммитом. Обычный коммит данных не получает тег приложения и не изменяет `pubspec.yaml` или APK `update.json`.
4. Дождаться успешной проверки исходников и прочитать публичный файл без авторизации. Проверить точные байты и подпись. Кэш CDN может некоторое время возвращать старый список; уже принятый более новый список этим не заменяется.

Команды из корня репозитория:

```bash
python tools/route_recommendations.py sign \
  --payload config/route_recommendations.json \
  --output updates/route-recommendations.json \
  --certificate config/route-recommendations-certificate.pem

python tools/route_recommendations.py verify \
  --envelope updates/route-recommendations.json \
  --payload config/route_recommendations.json \
  --certificate config/route-recommendations-certificate.pem
```

Если выходной файл уже существует, подпись новой версии сравнивается с ним и требует увеличения номера. Не удалять предыдущий конверт ради обхода этой проверки. При первоначальной публикации исходного файла ещё нет.

APK-кандидат и debug APK исключают из запуска коммиты, затрагивающие только эти два JSON и Markdown. Source checks продолжают проверять данные и подпись. Изменение кода механизма, сертификата, схемы или инструментов не попадает под это исключение.

## Порядок разработки после внедрения

Изменения поддерживаемых данных публикуются отдельным каналом. Исправления кода объединяются в законченный выпуск; новый APK предлагается при исправлении существенной ошибки, завершении полезной функции или изменении нативной части. Сам по себе коммит или новая рекомендация не означает, что пользователю нужно устанавливать приложение заново. Все обычные APK-выпуски сохраняют пакет и постоянный сертификат: [требования Android к подписи](https://developer.android.com/studio/publish/app-signing).
