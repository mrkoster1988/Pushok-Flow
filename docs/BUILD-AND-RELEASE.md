## Установка после v0.21.0

Эта debug-сборка подписана другим тестовым сертификатом, поэтому установить её поверх выданного ранее APK v0.21.0 нельзя. Перед переустановкой убедитесь, что исходная конфигурация WireGuard сохранена вне Pushok Flow или доступна у вашего VPN-провайдера. Удаление приложения очистит локальный профиль, исключения и память оценок Pushok ИИ. Затем удалите старую версию, установите v0.22.0 и добавьте профиль заново.

| APK | SHA-256 публичного сертификата подписи |
| --- | --- |
| v0.21.0, run 44811840135 | `c00a337f0be4db78dd2530f6bc5bddf5b22581fd5ecb2db60f07463af26ac89f` |
| v0.22.0, run 44817781185 | `06b3587b188b4dbab87917ce8851f49afd7cb6e172f468290ac786c20762f19b` |

Отпечатки получены из публичных сертификатов блока APK Signature Scheme v2. Это сравнение личности подписанта; оно не заменяет криптографическую проверку подписи Android. Требование совпадения сертификата при обновлении описано в [официальной документации Android](https://developer.android.com/studio/publish/app-signing#considerations).

В текущем workflow постоянный ключ не настроен: Android создаёт debug-ключ в окружении сборки. Перед регулярными обновлениями нужно настроить постоянный ключ подписи и его защищённое хранение в CI. Закрытый ключ и пароли не должны попадать в репозиторий или артефакты.

## Воспроизведение сборки

CI закрепляет Flutter `3.50.0`, Java 17, Kotlin CLI `2.2.21` для самостоятельных проверок и WireGuard `1.0.20260102`. Пакет интерфейса Material UI закреплён на `1.11.1`. Kotlin-компилятором Android-проекта управляет Gradle-шаблон Flutter.

1. В репозитории открыть **Actions → Android debug APK (unverified on device) → Run workflow**. Workflow также запускается при push в `main` и при pull request.
2. Проверить успешное завершение всех шагов. При сбое изучить `pushok-flow-android-build-diagnostics`.
3. Скачать `pushok-flow-debug-apk` и распаковать APK. Сверить SHA-256 с `apk-sha256.txt` из диагностического артефакта именно этого запуска.

Для локальной сборки с установленными Flutter, Android SDK, Java и Kotlin CLI:

```bash
python3 -m unittest discover -s tests -v
bash tools/bootstrap_android.sh
flutter pub get
bash tools/check_kotlin_routing.sh
flutter analyze lib test
flutter test --reporter expanded
python3 tools/check_android_manifest.py
flutter build apk --debug
python3 tools/verify_android_apk.py build/app/outputs/flutter-apk/app-debug.apk
sha256sum build/app/outputs/flutter-apk/app-debug.apk
```

Bootstrap создаёт временный Flutter-проект и переносит только Android-часть. Существующие исходники приложения, `pubspec.yaml`, тесты и документация сохраняются. Стандартный тест счётчика `MyApp` в проект не добавляется. Манифест сохраняет запрос `PROCESS_TEXT` и получает отдельный `MAIN`/`LAUNCHER` для списка приложений; резервное копирование защищённых профилей отключено.

## Следующий этап: физический Android

Успешная сборка подтверждает компиляцию и содержимое APK. Установка и VPN-подключение v0.22.0 ещё не проверены. Запись v0.21.0 подтверждает запуск, переходы по вкладкам, загрузку списка приложений, изменение переключателей исключений и работу локальных оценок Pushok ИИ; работа туннеля и маршруты трафика на ней не показаны. Результаты фиксируются в [задаче #1](https://github.com/mrkoster1988/Pushok-Flow/issues/1).

1. Установить debug APK на тестовый телефон, записать модель, версию Android и коммит сборки.
2. Без профиля нажать «Подключить». Должен открыться редактор с действием «Сохранить и подключить». Проверить пустое сохранение: подсказка должна остаться в редакторе и не появиться на вкладке «Маршруты» после закрытия.
3. Вставить тестовую конфигурацию кнопкой «Вставить», сохранить и подключиться, выдав системное разрешение VPN. Проверить подключение, отключение, DNS, IPv4 и IPv6. Перезапустить приложение и подключить сохранённый профиль без повторной вставки.
4. Выбрать приложение для прямого маршрута при выключенном туннеле; после подключения проверить, что его трафик идёт напрямую, а трафик остальных приложений — через туннель.
5. Проверить MAX, VK, банки, Ozon и Wildberries. Сам факт прямого маршрута не гарантирует принятие приложением активного системного VPN.
6. Проверить отказ в разрешении VPN, поворот экрана, возврат из фона и повторное подключение. Сопоставить состояние и uptime интерфейса с реальным туннелем.
7. Сверить внешний вид на телефоне с утверждёнными неоновыми макетами: фон, волны, круглая кнопка, фирменный рыжий маскот, светящиеся карточки и контурные иконки.

Приватные ключи, реальные VPN-конфигурации и персональные данные в Issues и журналы не добавляются. Выпуск подписанной release-сборки и проверка на устройстве остаются отдельными этапами.
