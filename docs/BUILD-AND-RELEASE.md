## Как получить воспроизводимый кандидат

CI закрепляет Flutter `3.50.0`, Java 17, Kotlin CLI `2.2.21`, Material UI `1.11.1` и WireGuard `1.0.20260102`. Компилятором Kotlin для Android-приложения управляет Gradle-шаблон Flutter.

1. Открыть **Actions → Android release candidate for persistent signing → Run workflow** для нужной ревизии. Workflow также запускается при изменениях кода в `main` и pull request.
2. Дождаться успешных проверок исходников, семи Kotlin-модулей, анализа Dart, Flutter-тестов, манифеста и `flutter build apk --release --no-pub`.
3. Скачать кандидат и инструменты подписи из одного запуска. Проверить их контрольные суммы и `sourceCommit` в метаданных.
4. Выполнить локальную подпись и проверку по [UPDATES.md](UPDATES.md). В таблицу выше записать SHA-256 и размер окончательного подписанного APK.
5. Опубликовать APK, `.sha256` и `update.json` вместе в GitHub Release и проверить публичные файлы. В v0.24.0 для этого использован `publish-verified-update.yml`, который восстанавливает и проверяет уже подписанный файл без закрытого ключа в CI; порядок описан в [UPDATES.md](UPDATES.md).

| Артефакт Actions | Содержимое | Хранение |
| --- | --- | --- |
| `pushok-flow-release-candidate` | `Pushok-Flow-v0.24.0-candidate.apk`, его `.sha256`, `candidate.json`, пояснение к подписи | 30 дней |
| `pushok-flow-android-signing-tools` | Официальные Android SDK Build Tools для Linux x86_64, метаданные и контрольные суммы | 30 дней |
| `pushok-flow-candidate-diagnostics` | Версии инструментов, журналы bootstrap, анализа, тестов и сборки | 14 дней |

Для коммита этого APK успешно пройдены 114 Python-тестов, 40 Flutter-тестов, анализ Dart и три исполняемые Kotlin-проверки: `WireGuardRouting`, `TunnelHealth`, `UpdatePolicy`. Release-кандидат собран и проверен; после постоянной подписи отдельно проверены окончательные SHA-256, размер, сертификат и содержимое APK. В APK присутствуют библиотеки WireGuard для `arm64-v8a`, `armeabi-v7a` и `x86_64`; исходное изображение маскота сохранено.

### Локальная сборка кандидата

Нужны Flutter, Android SDK, Java и Kotlin CLI:

```bash
python3 -m unittest discover -s tests -v
bash tools/bootstrap_android.sh
python3 tools/fetch_xray_android.py
flutter pub get --enforce-lockfile
git diff --exit-code -- pubspec.lock
bash tools/check_kotlin_routing.sh
flutter analyze lib test --no-pub
flutter test --no-pub --reporter expanded
python3 tools/check_android_manifest.py
flutter build apk --release --no-pub
python3 tools/verify_android_apk.py build/app/outputs/flutter-apk/app-release.apk
```

При стандартном сгенерированном Android-проекте этот результат ещё требует подписи постоянным ключом. Для окончательного APK `verify_release_apk.py` проверяет сертификат, подпись, пакет, версию, SDK, отсутствие режима отладки и необходимые компоненты. Выравнивание отдельно проверяется через `zipalign -c -P 16 4`. Скрипт `create_update_manifest.py` формирует публичные файлы выпуска. Команды подписи и требования к хранению ключа приведены в [UPDATES.md](UPDATES.md).

Bootstrap переносит только Android-часть временного Flutter-проекта, затем подключает нативный мост, updater и его ограниченный FileProvider. Исходники Flutter, `pubspec.yaml`, тесты и документация сохраняются. Резервное копирование защищённых профилей отключено.

Начиная с v0.36.0 отдельный шаг `fetch_xray_android.py` загружает официальный libXray v26.11.9 только на машине сборки. Он проверяет точные SHA-256 и размеры ZIP/AAR, наличие четырёх ABI и выравнивание ELF под страницы 16 КиБ. APK включает нужные Flutter ABI и лицензии; установленное приложение не загружает исполняемый код. Служба Xray обязана оставаться в отдельном приватном процессе `:xray`.

Workflow `android-release.yml` для подписи и публикации через GitHub secrets запускается автоматически при `push` в `main`, изменяющем `pubspec.yaml`, а также вручную через `workflow_dispatch`. Для подписи нужны четыре корректно настроенных signing secrets. При ошибке конфигурации CI-подписи действует описанный в [UPDATES.md](UPDATES.md) путь: успешный CI точного исходного коммита, локальная подпись кандидата сохранённым постоянным ключом, проверка APK и публикация через `publish-public-release.yml`. Этот путь использован для [v2.0.11](release-checks/v2.0.11.md); обязательные проверки и постоянный сертификат сохраняются.

В v0.24.0 постоянная подпись выполнена локально, а `publish-verified-update.yml` передал проверенный результат в GitHub Release без ключа подписи в CI. Debug workflow остаётся средством разработки, а регулярный канал обновлений использует постоянный сертификат.

## Переход с прежних debug-сборок

Ранее выданные debug APK подписаны временными сертификатами. Сертификат v0.24.0 другой, поэтому обновление поверх такой установки Android не примет. Потребуется однократная переустановка: сначала сохранить исходный WireGuard `.conf` вне приложения и записать выбранные исключения, затем удалить старую версию и установить подписанный v0.24.0. Удаление очищает профиль, исключения и локальную память оценок Pushok ИИ.

После перехода следующие APK с тем же постоянным сертификатом и большим `versionCode` предназначены для обновления на месте с сохранением данных. Совпадение сертификата требуется Android для обновления приложения: [официальная документация о подписи](https://developer.android.com/studio/publish/app-signing#considerations). Сам сценарий обновления и сохранение данных на конкретном телефоне ещё должны быть проверены.

## Что подтверждено записью телефона

Запись установленной v0.22.0 подтверждает запуск, переходы по вкладкам, изменение исключений, локальные оценки Pushok ИИ и очистку памяти. Редактор открывается при подключении без профиля; ошибка профиля остаётся в нём. На записи обнаружено перекрытие кнопки сохранения системной панелью Android. Исправление SafeArea и пояснение о непригодности отдельного UUID включены в v0.24.0 через промежуточную v0.23.0.

Запись v0.22.0 не подтверждает успешное сохранение полного рабочего профиля, соединение Flow VPN, DNS или маршруты трафика. Результат сборки и widget-тесты также не подтверждают обновление на физическом телефоне.

## Проверка v0.24.0 на устройстве

1. Записать модель телефона, Android, версию APK и исходный коммит. При переходе с debug выполнить предварительное сохранение конфигурации, описанное выше.
2. Открыть **Профиль → Версия и обновления**, проверить установленную версию и явную проверку выпуска. Если новее v0.24.0 ещё ничего не опубликовано, состояние «Установлена последняя версия» ожидаемо.
3. При следующем выпуске с большим номером сборки пройти весь путь: загрузка → проверка APK → разрешение в настройках → возврат → отдельное подтверждение установки. Проверить отмену, пересоздание приложения и повторное открытие готового файла. После обновления проверить сохранность WireGuard-профиля, исключений и локальных оценок.
4. Открыть редактор с главной и из «Серверов». Проверить нижнюю кнопку при трёхкнопочной навигации Android, раскрытом поле и открытой клавиатуре; отдельный UUID должен получать понятное объяснение.
5. С рабочим полным `.conf` проверить VPN-подключение, отключение, DNS, IPv4/IPv6 и подключение сохранённого профиля после перезапуска. Проверить прямой трафик выбранных приложений и туннель для остальных.
6. Проверить отказ в разрешении VPN, возврат из фона и соответствие состояния/uptime настоящему туннелю. Зафиксировать результаты в [задаче #1](https://github.com/mrkoster1988/Pushok-Flow/issues/1).

Реальные конфигурации, приватные ключи и персональные данные в отчёт, запись экрана и журналы не включаются.
