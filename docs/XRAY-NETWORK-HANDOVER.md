# VLESS: смена физической сети

## Причина изменения

До v0.47.0 `XrayVpnService` выбирал адрес системного DNS один раз при подключении.
После потери Wi-Fi этот адрес мог оставаться привязанным к уже недоступной сети.
`VpnService.protect()` исключал сокеты ядра из собственного TUN, но не закреплял их
за той же физической сетью, через которую выполнялось разрешение имени сервера.

Исправление сохраняет один экземпляр ядра и TUN на время пользовательского
подключения. Меняется снимок физической сети для новых исходящих сокетов и
разрешения имени сервера. Перенести уже установленный TCP-сеанс на другой
`Network` этим механизмом нельзя; повторное открытие соединений остаётся задачей
транспорта Xray и использующего его приложения.

## Постоянный локальный DNS

В отдельном процессе `:xray` создаётся один локальный посредник UDP/TCP на
`127.0.0.1` и одном выделенном порту. `LibXray.setDNS()` получает его адрес перед
первым запуском ядра. Повторной замены глобального resolver или `resetDNS()` в
живом процессе нет: прекращение работы Xray не доказывает завершение всех
старых операций Go.

Посредник принимает только один вопрос класса `IN`, типа `A` или `AAAA`, для
точного имени текущего VLESS-сервера. Имя сравнивается без учёта регистра и
завершающей точки. Вопросы для остальных имён не передаются наружу. Ограничены
размер сообщения, количество вопросов, допустимые дополнительные записи,
время ожидания и количество рабочих задач. Ответы синтезируются из адресов
Android с TTL 0; при превышении размера UDP используется признак усечения и
повтор по TCP. Ошибка платформенного разрешения не объявляется доказательством
отсутствия имени: возвращается `SERVFAIL`.

Разрешение выполняет `Network.getAllByName()` выбранной физической сети.
Сохраняются системная обработка Private DNS, IPv4/IPv6 и DNS64. Приложение не
пересылает этот запрос самостоятельно незашифрованным пакетом на адрес из
`LinkProperties` и не подменяет его резервным публичным DNS. Это относится к
имени самого сервера; DNS-пакеты приложений продолжают идти через существующий
TUN и VLESS.

Каждый запрос захватывает сеть, разрешённое имя и поколение подключения.
Актуальность проверяется перед разрешением и перед выдачей результата.
Опоздавший результат старой сети или остановленного подключения не применяется.
Зависший системный вызов продолжает занимать свой ограниченный рабочий слот до
фактического завершения; таймаут не создаёт заменяющий поток без ограничения.

Используются два потока платформенного разрешения и отдельный неблокирующий
цикл обслуживания локальных сокетов. Одновременно допускаются не более двух
разрешений, 16 ожидающих запросов, четырёх готовых результатов и четырёх TCP-клиентов.
Ожидание DNS ограничено двумя секундами; фаза чтения или записи TCP — одной
секундой. Входной пакет ограничен 4096 байтами, UDP-ответ — 512 байтами либо
объявленным EDNS-размером не более 1232 байт, TCP-ответ — 65535 байтами.

## Сокеты и владение

Новый исходящий сокет ядра сначала исключается из TUN через `protect()`, затем
привязывается к выбранному `Network` до соединения. Для Java binding используется
дубликат исходного FD: закрытие временного `ParcelFileDescriptor` не передаёт и
не отнимает владение FD у Go. Ошибка или исчезновение выбранной сети не разрешает
открыть непривязанный сокет. `setUnderlyingNetworks()` сообщает Android ту же
сеть; этот вызов сам по себе не выполняет binding.

Локальный DNS-сокет использует отдельный protect-only controller. Его нельзя
привязывать к Wi-Fi или мобильной сети: назначение находится на loopback.
Разрешение `CHANGE_NETWORK_STATE` необходимо для binding к фоновой физической
сети; оно проверяется в исходном manifest и в готовом APK начиная с versionCode 47.

Наблюдение сети начинается только в рамках явного подключения пользователя.
Изменение сети не запускает новое ядро, не меняет профиль и не создаёт новую
пользовательскую сессию. При отсутствии физической сети сохраняются TUN и
намерение подключения. STOP, отзыв системного разрешения и уничтожение сервиса
сначала инвалидируют назначение, затем выполняют обычную последовательную
очистку. Поздний callback не получает право включить подключение заново.

Подходят физические сети `INTERNET + NOT_VPN` с готовыми link properties и без
явного captive portal. Приоритет получают `VALIDATED`, затем `NOT_METERED`;
при равенстве сохраняется текущая сеть. Единственная пригодная сеть без
`VALIDATED` разрешена: результат системной проверки Android не доказывает
доступность или недоступность VLESS-сервера. События объединяются с ограниченным
ожиданием 250 мс. На API 24/25 недостающие начальные сведения о вновь появившейся
сети читаются вне callback; данные упорядоченных callbacks имеют приоритет над
потенциально устаревшим синхронным снимком.

## Статус службы и интерфейса

Внутренний ответ `STATUS` службы Xray содержит следующие поля:

| Поле | Значение |
|---|---|
| `connected` | Подтверждённое локальное ядро и выбранная физическая сеть доступны. Это не проверка удалённого сервера. |
| `ownsTunnel` | Подключение удерживает ресурсы или пользовательское намерение, включая ожидание сети. |
| `state` | `connected`, `disconnected`, `waiting_network`, `reconnecting` или `unknown`. |

Верхний MethodChannel `vpnStatus` дополнительно использует `transitioning`
на время явной операции пользователя, защищённой `ProfileOperationGate`.

Во время ожидания и восстановления интерфейс не показывает подтверждённое UP
или прежние показатели передачи. Кнопка отключения доступна; повторное
подключение, изменение профиля/маршрутов и установка обновления ограничиваются
владением ресурсами, а не только флагом UP. Неизвестное или противоречивое
сообщение не превращается в разрешение изменять активное подключение.

Исходная команда START и сетевые события имеют разные поколения. Смена сети
не инвалидирует ожидающий ответ START и не позволяет его устаревшей обработке
ошибки остановить более новый сеанс. Существующая проверка поколения при
доставке результата Xray сохраняется.

## Границы проверки

Исполняемые JVM-проверки используют реальные классы разбора DNS, ограниченного
исполнения, выбора сети и состояния; сетевые ответы в них синтетические.
Flutter-проверки проверяют отображение ожидания, доступность STOP и защиту от
опоздавших ответов. CI собирает настоящий Android APK и проверяет разрешения,
изоляцию процесса, подпись, ABI и native-библиотеки.

Проверка на физическом телефоне должна отдельно покрыть Wi-Fi → мобильную сеть
и обратный переход, отсутствие обеих сетей, возврат сети, STOP во время ожидания,
частный DNS, IPv6, RAW/TLS/REALITY, WebSocket и gRPC. Автоматические проверки не
подтверждают непрерывность каждого удалённого сеанса или скорость восстановления
конкретного оператора.
