**Автообновление включено по умолчанию.** Фоновая задача проверяет опубликованный выпуск, скачивает новую версию и проверяет размер, SHA-256, пакет, номер версии и постоянный сертификат. Открывать экран обновлений или нажимать «Скачать» для этого не требуется. Периодические фоновые проверки планируются примерно раз в шесть часов; отдельная проверка также планируется после запуска приложения и системного события замены APK. Фактическое время выбирает Android. Используется доступное интернет-соединение, включая мобильную сеть. При недостаточном заряде, нехватке места или отсутствии сети Android откладывает задачу.

Готовый APK хранится в приватном постоянном каталоге приложения. Сбой сети и закрытие экрана не должны удалять уже проверенный файл. Следующая версия становится готовой только после полной проверки. Отключить автоматический режим можно в **Профиль → Версия и обновления → Автообновление**; ручные действия остаются доступны.

### Когда приложение обновляется само

На Android 12 / API 31 и новее Flow использует штатный `PackageInstaller` и запрашивает установку без действий пользователя. Android проверяет допуск на установку из этого приложения и свои условия для самостоятельного обновления. Разрешение на установку можно выдать заранее кнопкой **Разрешить установку**. Приложение не открывает системные настройки самопроизвольно.

Установка ожидает завершения активного соединения и ухода приложения с экрана: обычная замена APK останавливает процессы приложения. Если Android требует подтверждение, готовый файл остаётся в ожидании. На Android 7–11 проверка и загрузка тоже автоматические, но установка выполняется пользователем через системный экран. Несовместимая подпись не запускает удаление приложения.

Для первого перехода с 0.36 или более раннего выпуска нужен один обычный APK поверх установленной подписанной версии. Промежуточные версии устанавливать не требуется. После этого автоматический механизм обслуживает следующие выпуски.

Технические основания: [условия самостоятельной установки Android](https://developer.android.com/reference/android/content/pm/PackageInstaller.SessionParams#setRequireUserAction(int)), [системное расписание и ограничения WorkManager](https://developer.android.com/develop/background-work/background-tasks/persistent/getting-started/define-work), [закреплённая библиотека WorkManager 2.11.2](https://developer.android.com/jetpack/androidx/releases/work#2.11.2).

## Обновления без удаления и отдельные обновления данных

Удалять Pushok Flow для обычного обновления не нужно: APK устанавливается поверх существующего приложения с прежним постоянным сертификатом. Последующие выпуски сохраняют идентичность приложения и его хранилищ. Ошибка проверки или загрузки обновления не является основанием удалять приложение.

Начиная с v0.34.0 работает отдельный канал рекомендаций по приложениям: такие данные обновляются внутри «Маршрутов», без APK и системного установщика. Механизм впервые вошёл в APK v0.34.0 и сохраняется в более новых выпусках; устанавливать v0.34.0 как промежуточную версию не требуется. Новая версия списка не требует выпуска приложения. Код Flutter, Kotlin и WireGuard обновляется полноценным APK. [Устройство механизма и порядок выпуска данных](NO-APK-UPDATES.md).

Старый или противоречивый ответ сообщает об ошибке проверки, а не об отсутствии новых версий; уже подготовленный файл сохраняется. Раздел показывает этап и время последней успешной проверки, позволяет проверить ещё раз перед скачиванием или установкой и обновляет состояние после возврата из фона.

В v0.31.0–v0.36.0 отметка времени относится к успешной проверке в текущем процессе приложения, а не к гарантии глобальной свежести GitHub. ## Ручное обновление и первый переход на v0.37.0

1. Нажать **Проверить обновления**.
2. Если доступна новая версия, нажать **Скачать** и дождаться проверки файла.
3. При первом обновлении нажать **Разрешить установку**, разрешить установки из Pushok Flow в настройках Android и вернуться в приложение.
4. Нажать **Установить обновление** и подтвердить действие в системном окне Android.

При обычном обновлении поверх приложения его данные сохраняются. Если установка отменена, проверенный файл остаётся доступен для повторного нажатия; при восстановлении приложения файл проверяется заново. В версиях до 0.37 очистка кэша Android может удалить скачанный APK — в таком случае его нужно скачать повторно. С 0.37 проверенный APK хранится отдельно от кэша.

### Как опубликован тот же подписанный APK

Workflow [publish-verified-update.yml](../.github/workflows/publish-verified-update.yml) получил точный CI-кандидат и проверил его запуск, исходный коммит и контрольную сумму артефакта. В описании находятся только публичные байты APK; закрытый ключ и пароли в GitHub Actions не передавались.

Перед публикацией workflow проверил точные итоговые размер и SHA-256, постоянный сертификат через `verify_release_apk.py`, затем создал тег на исходном коммите APK и черновик выпуска. Коммит с инструментами публикации может быть новее коммита приложения; тег `v0.24.0` указывает именно на `355813cbf74a8f69a9cdf4c83869faa9d7b46b13`.

В [первом запуске публикации](https://github.com/mrkoster1988/Pushok-Flow/actions/runs/44874652222) восстановление, проверка APK и загрузка файлов завершились успешно, но запрос черновика по тегу вернул HTTP 404. Это не успешный запуск workflow целиком; его обращение к черновику исправлено на запрос по ID выпуска.

Отдельный [verify-published-update.yml](../.github/workflows/verify-published-update.yml) проверяет публичный адрес обновлятора без учётных данных: ровно 431 байт, SHA-256 `89224573d16faf703f32182039f9332357c3bd016a0c0f357122462d3e5dc3c8` и все поля v0.24.0. Этот workflow закреплён за первым выпуском v0.24.0, оставлен только для ручного запуска и намеренно отказывается работать при существующем теге или опубликованном latest. Для следующей версии его нельзя просто запустить повторно или заменить только JSON: потребуется отдельная проверенная процедура публикации либо настроенный ручной `android-release.yml`.

## Как подготовить следующий выпуск

1. Объединить законченные изменения в один выпуск. Увеличить версию и `versionCode` в `pubspec.yaml`, обновить отображаемую версию в информации о приложении.
2. Дождаться успешных проверок исходников и workflow **Android release candidate** для точного коммита.
3. Скачать общий артефакт с четырьмя APK-кандидатами и набор официальных Android SDK Build Tools из того же запуска. Кандидаты ещё не являются распространяемыми подписанными выпусками.
4. Подписать все четыре кандидата одним сохранённым постоянным ключом. Не создавать новый ключ при каждом выпуске. Ключ и пароли должны храниться вне репозитория и публичных артефактов.
5. Проверить каждый подписанный APK через `tools/verify_release_apk.py`: universal без `--abi`, самостоятельные варианты с явным `--abi arm64-v8a`, `--abi armeabi-v7a` или `--abi x86_64`. Сохранить `verified-release.json` и три `verified-release-<ABI>.json`. Все файлы должны иметь одинаковые packageName, versionName, versionCode, minSDK и сертификат.
6. Сформировать файлы через `tools/create_update_manifest.py --variants-dir <DIR>` и описание публикации через `tools/create_public_release_delta.py --variants-dir <DIR>`. Schema 2 описания содержит четыре APK; публичных assets ровно **девять: четыре APK, четыре `.sha256` и один `update.json`**. Сам `update.json` остаётся schema 1 и указывает на universal. Для прежних описаний schema 1 сохраняются один APK и три публичных assets.
7. Убедиться, что номер сборки больше опубликованного в актуальном `update.json`, а сертификат совпадает. Зафиксировать описание в `release-staging/v<VERSION>.json` и запустить штатный workflow публикации с этой версией. Он проверит исходный CI, восстановит подписанные файлы, загрузит полный черновик и сравнит все размеры/SHA-256 перед публикацией как latest. Тег должен указывать на точный исходный коммит APK; существующие версии не заменяются.
8. Проверить без авторизации latest API, общий и адресный `update.json`, а также полные байты всех APK и checksum. Сохранить результаты. Только успешная публикация и проверки публичного канала подтверждают доступность выпуска обновлятору.

### Проверенная публикация с локальной подписью

Штатный ручной workflow [publish-public-release.yml](../.github/workflows/publish-public-release.yml) принимает только номер версии, например `0.40.0`. Он читает соответствующий отслеживаемый `release-staging/v<VERSION>.json`; произвольные пути, адреса или ID выпуска в input не принимаются. Старый `publish-verified-update.yml` остаётся историческим инструментом первого v0.24.0.

После локальной подписи [create_public_release_delta.py](../tools/create_public_release_delta.py) формирует ограниченное публичное описание различий между точными CI-кандидатами и окончательными подписанными APK. Schema 2 содержит universal и ровно три ABI-варианта. Генератор для каждого файла сверяет состав и сжатые данные приложения; изменение кода или ресурсов при подписи запрещено. Все четыре локальных восстановления проверяются побайтово. Закрытый ключ и пароли в этот файл не включаются; содержатся только публичные байты APK, реквизиты CI и примечания выпуска. Старые описания schema 1 с одним APK поддерживаются прежним путём.

Workflow проверяет успешность обоих CI-запусков одного коммита, идентичность общего артефакта и неизменность прежнего публичного канала. Каждый восстановленный APK повторно проверяется Android SDK: подпись, постоянный сертификат, пакет, версия, минимальный SDK, отсутствие debug-флага, VPN-сервисы, состав ABI и выравнивание. Затем создаются и сверяются прежний `update.json` для universal и отдельные checksum всех APK.

Новый тег указывает на точный коммит APK. Черновик создаётся через API; его числовой ID из ответа используется для загрузки и последующей проверки. Перед публикацией сверяется полный набор: **девять файлов для schema 2 или три для прежней schema 1**, их размеры, SHA-256, идентификаторы и прежний latest. Существующие теги, выпуски и файлы не перезаписываются. После публикации без авторизации проверяются оба пути манифеста, latest API и полные байты всех APK/checksum.

В ответах GitHub для черновика допустим временный путь `untagged-<hex>`. Publisher получает его только из проверенного `html_url` этого же draft и требует точного соответствия URL всех assets. После публикации разрешены только канонические адреса с тегом `v<VERSION>`. Это исправление потребовалось при первой публикации v0.40; байты девяти уже загруженных файлов сохранились.

### Возобновление полного неопубликованного черновика

Обычный путь без плана восстановления по-прежнему требует отсутствия тега, опубликованного выпуска и черновика. Слепой повторный запуск после частичной публикации останавливается. Сначала нужно независимо проверить существующий draft и полный набор уже загруженных файлов.

Для возобновления конкретного **полного, ещё ни разу не опубликованного** черновика используется единственный явный файл `release-staging/v<VERSION>-resume.json`, зафиксированный в Git. Его байты должны точно совпадать с файлом в текущем `HEAD`; изменённый локальный, неотслеживаемый файл или символическая ссылка не принимаются. План связывает repository, tag, sourceCommit, releaseId, SHA-256 основного staging JSON и точные ID всех ожидаемых assets.

Перед действием повторно проверяются successful CI, артефакт, прежний публичный канал, исходный lightweight tag, название и описание выпуска, состояние `draft=true`, `prerelease=false`, `published_at=null`, все ID/размеры/SHA-256 и адреса assets. Подписанные APK заново восстанавливаются и проходят обычную проверку. Изменение черновика между проверками останавливает публикацию.

При совпадении всех данных штатный workflow выполняет только перевод **того же** draft в опубликованный latest. Новый тег, новый release или новые assets не создаются; существующие файлы не удаляются и не загружаются повторно. Workflow и его input остаются прежними — только `release_version`. Для v0.40 применён [зафиксированный план](../release-staging/v0.40.0-resume.json): выпуск `454631088`, исходный коммит `3b1f8672686e99ddadf2b5fffb9ca972bc41812f`, все девять прежних ID и файлов сохранены.

Уже опубликованный выпуск этот путь не принимает, даже если план остался в истории. Если после публикации не завершилась проверка канала, повторяют только операции чтения, а не публикацию.

Пример локальной подписи и проверки одного универсального APK с установленными Android SDK Build Tools и Java. Пароли вводятся по запросу `apksigner`, а не записываются в команду или документацию:

```bash
zipalign -P 16 -f 4 app-release.apk app-aligned.apk
apksigner sign --ks /private/path/pushok-flow-release.p12 \
  --ks-key-alias pushok-flow-release --v4-signing-enabled false \
  --out app-signed.apk app-aligned.apk
python3 tools/verify_release_apk.py app-signed.apk \
  --expected-certificate-sha256 8b4114881116a920c3351b503052ac27078fdbbfcae1ace27f1af8245ebb7047 \
  --output release-verification.json
python3 tools/create_update_manifest.py --apk app-signed.apk \
  --verified release-verification.json --output dist
```

Для полного выпуска schema 2 подпись повторяется для каждого ABI-кандидата. Каждый вариант проверяется с явным `--abi` и сохраняется как `Pushok-Flow-v<VERSION>-<ABI>.apk`, его отчёт — как `verified-release-<ABI>.json`. В окончательный вызов `create_update_manifest.py` и генератор staging добавляется `--variants-dir <DIR>` с тремя подписанными вариантами и отчётами; одного примера universal выше для публикации девяти assets недостаточно.

### Будущий вариант с GitHub secrets

`android-release.yml` содержит отдельный workflow для подписи и публикации после настройки четырёх GitHub Actions secrets: `PUSHOK_ANDROID_KEYSTORE_BASE64`, `PUSHOK_ANDROID_KEYSTORE_PASSWORD`, `PUSHOK_ANDROID_KEY_ALIAS`, `PUSHOK_ANDROID_KEY_PASSWORD`. Он запускается только вручную; без этих secrets намеренно завершится ошибкой. Этот вариант не активирован. В v0.24.0 постоянная подпись выполнена локально, а `publish-verified-update.yml` передал тот же проверенный APK в GitHub Release без закрытого ключа в CI.

## Что подтверждается отдельно

Успешная сборка и проверка подписи подтверждают пригодность файла к передаче тестировщику. Реальное обновление на конкретном телефоне, сохранность его данных и работа VPN проверяются на устройстве. Первая версия с механизмом обновления может показать «Установлена последняя версия»; полный сценарий обновления проверяется при публикации следующего выпуска с большим номером сборки.
