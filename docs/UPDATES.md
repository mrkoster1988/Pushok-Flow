# Обновления Pushok Flow на Android

> **Известное предупреждение v0.24.0:** после выдачи APK получен скриншот блокировки Pushok Flow в Play Protect. Позднейшие скриншоты показывают работающую v0.24.0, но не подтверждают снятие предупреждения. Функциональные обновления сохраняют пакет и постоянный сертификат; устранение классификации Google ими не заявляется. [Диагностика](PLAY-PROTECT-v0.24.0.md).

Начиная с v0.24.0, в **Профиль → Версия и обновления** можно проверить выпуск, скачать APK и открыть системное подтверждение обновления. Проверка и загрузка запускаются кнопками. Приложение не устанавливает обновления без действия пользователя.

## Порядок для пользователя

1. Нажать **Проверить обновления**.
2. Если доступна новая версия, нажать **Скачать** и дождаться проверки файла.
3. При первом обновлении нажать **Разрешить установку**, разрешить установки из Pushok Flow в настройках Android и вернуться в приложение.
4. Нажать **Установить обновление** и подтвердить действие в системном окне Android.

При обычном обновлении поверх приложения его данные сохраняются. Если установка отменена, проверенный файл остаётся доступен для повторного нажатия; при восстановлении приложения файл проверяется заново. Очистка кэша Android может удалить скачанный APK — в таком случае его нужно скачать повторно.

### Однократный переход со старых debug APK

Прежние сборки создавались с временными debug-ключами. Постоянный сертификат v0.24.0 отличается от сертификатов ранее выданных debug APK. Если такая версия установлена, потребуется один раз удалить её и установить подписанный v0.24.0. Перед удалением сохраните исходный WireGuard `.conf` вне приложения: удаление очищает профиль, исключения и локальные оценки Pushok ИИ. Последующие выпуски должны использовать тот же постоянный ключ и больший `versionCode`.

## Канал выпусков

Версии v0.25 и v0.26 существовали как проверенные CI-кандидаты, но не публиковались в этот канал. Поэтому v0.24.0 правильно показывала отсутствие новой опубликованной версии. Эти изменения объединены с последующими исправлениями в готовящийся выпуск v0.27.0.

- Репозиторий: `mrkoster1988/Pushok-Flow`.
- Описание актуального выпуска: `https://github.com/mrkoster1988/Pushok-Flow/releases/latest/download/update.json`.
- APK: `https://github.com/mrkoster1988/Pushok-Flow/releases/download/v<VERSION>/Pushok-Flow-v<VERSION>.apk`.
- Пакет: `shop.pushok.flow`; минимальная версия Android: API 24.
- SHA-256 постоянного публичного сертификата: `8b4114881116a920c3351b503052ac27078fdbbfcae1ace27f1af8245ebb7047`.

Схема `update.json` закреплена в `UpdatePolicy.kt`: версия схемы, имя пакета, версия приложения, номер сборки, минимальный SDK, адрес APK, его SHA-256, размер и отпечаток сертификата. Не добавляйте произвольные поля в схему 1.

Проверка принимает HTTPS-адреса этого репозитория и разрешённые адреса доставки файлов GitHub. Перед установкой проверяются размер и SHA-256 файла, пакет, версия, минимальный SDK, единственный текущий сертификат и превышение установленного номера сборки. Закрытый ключ подписи в APK, `update.json` и исходники не включается.

### Как опубликован тот же подписанный APK

Workflow [publish-verified-update.yml](../.github/workflows/publish-verified-update.yml) получил точный CI-кандидат и проверил его запуск, исходный коммит и контрольную сумму артефакта. Скрипт [restore_signed_apk.py](../tools/restore_signed_apk.py) применил компактное публичное описание различий из [release-staging/v0.24.0.json](../release-staging/v0.24.0.json) и восстановил побайтно тот же APK, который был подписан локально. В описании находятся только публичные байты APK; закрытый ключ и пароли в GitHub Actions не передавались.

Перед публикацией workflow проверил точные итоговые размер и SHA-256, постоянный сертификат через `verify_release_apk.py`, затем создал тег на исходном коммите APK и черновик выпуска. Выпуск стал latest после загрузки и проверки всех трёх файлов. Повторная сборка или новая подпись на сервере не выполнялись. Коммит с инструментами публикации может быть новее коммита приложения; тег `v0.24.0` указывает именно на `355813cbf74a8f69a9cdf4c83869faa9d7b46b13`.

В [первом запуске публикации](https://github.com/mrkoster1988/Pushok-Flow/actions/runs/44874652222) восстановление, проверка APK и загрузка файлов завершились успешно, но запрос черновика по тегу вернул HTTP 404. После отдельной проверки ID выпуска, исходного тега, размеров и SHA-256 всех трёх assets черновик опубликован через интерфейс GitHub. Это не успешный запуск workflow целиком; его обращение к черновику исправлено на запрос по ID выпуска.

Отдельный [verify-published-update.yml](../.github/workflows/verify-published-update.yml) проверяет публичный адрес обновлятора без учётных данных: ровно 431 байт, SHA-256 `89224573d16faf703f32182039f9332357c3bd016a0c0f357122462d3e5dc3c8` и все поля v0.24.0. Это проверка первого опубликованного выпуска; после появления новой версии ожидаемые значения нужно обновить.

Этот workflow закреплён за первым выпуском v0.24.0, оставлен только для ручного запуска и намеренно отказывается работать при существующем теге или опубликованном latest. Для следующей версии его нельзя просто запустить повторно или заменить только JSON: потребуется отдельная проверенная процедура публикации либо настроенный ручной `android-release.yml`.

## Как подготовить следующий выпуск

1. Объединить законченные изменения в один выпуск. Увеличить версию и `versionCode` в `pubspec.yaml`, обновить отображаемую версию в информации о приложении.
2. Дождаться успешных проверок исходников и workflow **Android release candidate** для точного коммита.
3. Скачать APK-кандидат и набор официальных Android SDK Build Tools из артефактов того же запуска. Кандидат ещё не является распространяемым подписанным выпуском.
4. Подписать кандидат сохранённым постоянным ключом. Не создавать новый ключ при каждом выпуске. Ключ и пароли должны храниться вне репозитория и публичных артефактов.
5. Проверить подписанный APK через `tools/verify_release_apk.py`, затем сформировать три публичных файла через `tools/create_update_manifest.py`.
6. Убедиться, что номер сборки больше опубликованного в актуальном `update.json`, а сертификат совпадает. Создать новый черновик GitHub Release и загрузить проверенный APK, его `.sha256` и `update.json` вместе. Тег `v<VERSION>` должен указывать на исходный коммит APK. Проверить размеры и контрольные суммы всех трёх загруженных файлов, затем опубликовать выпуск как latest. Существующие версии не заменять.
7. Проверить публичный `update.json` и соответствие файлов. Тогда установленное приложение сможет обнаружить новую версию.

### Проверенная публикация с локальной подписью

Новый ручной workflow [publish-public-release.yml](../.github/workflows/publish-public-release.yml) принимает только номер версии, например `0.27.0`. Он читает соответствующий отслеживаемый `release-staging/v<VERSION>.json`; произвольные пути и адреса в input не принимаются. Старый `publish-verified-update.yml` остаётся историческим инструментом первого v0.24.0.

После локальной подписи [create_public_release_delta.py](../tools/create_public_release_delta.py) формирует ограниченное публичное описание различий между точным CI-кандидатом и окончательным подписанным APK. Генератор сверяет состав и сжатые данные файлов приложения; изменение кода или ресурсов при подписи запрещено. Он проверяет локальное восстановление побайтно. Закрытый ключ и пароли в этот файл не включаются; содержатся только публичные байты APK, реквизиты CI и примечания выпуска.

Workflow проверяет успешность обоих CI-запусков одного коммита, идентичность артефакта и неизменность прежнего публичного канала. Восстановленный APK повторно проверяется Android SDK: подпись, постоянный сертификат, пакет, версия, минимальный SDK, отсутствие debug-флага, VPN-сервис и выравнивание. Затем создаются и сверяются `update.json` и SHA-256.

Новый тег указывает на точный коммит APK. Черновик создаётся через API; его числовой ID из ответа используется для загрузки и последующей проверки. Перед публикацией сверяются ровно три файла, их размеры и SHA-256, а также прежний latest. Существующие теги, выпуски и черновики не перезаписываются. После публикации публичный адрес обновлятора проверяется без авторизации: байты `update.json` должны совпасть с проверенным файлом.

Если шаг остановился после создания тега или черновика, сначала нужно проверить его состояние и загруженные файлы. Слепой повторный запуск намеренно отклоняется, чтобы не заменить уже проверенные данные.

Пример локальной подписи и проверки с установленными Android SDK Build Tools и Java. Пароли вводятся по запросу `apksigner`, а не записываются в команду или документацию:

```bash
zipalign -P 16 -f 4 app-release.apk app-aligned.apk
apksigner sign --ks /private/path/pushok-flow-release.p12 \
  --ks-key-alias pushok-flow-release --v4-signing-enabled false \
  --out app-signed.apk app-aligned.apk
python3 tools/verify_release_apk.py app-signed.apk \
  --expected-certificate-sha256 8b4114881116a920c3351b503052ac27078fdbbfcae1ace27f1af8245ebb7047 \
  --output release-verification.json
python3 tools/create_update_manifest.py --apk app-signed.apk \
  --verified release-verification.json --output dist
```

### Будущий вариант с GitHub secrets

`android-release.yml` содержит отдельный workflow для подписи и публикации после настройки четырёх GitHub Actions secrets: `PUSHOK_ANDROID_KEYSTORE_BASE64`, `PUSHOK_ANDROID_KEYSTORE_PASSWORD`, `PUSHOK_ANDROID_KEY_ALIAS`, `PUSHOK_ANDROID_KEY_PASSWORD`. Он запускается только вручную; без этих secrets намеренно завершится ошибкой. Этот вариант не активирован. В v0.24.0 постоянная подпись выполнена локально, а `publish-verified-update.yml` передал тот же проверенный APK в GitHub Release без закрытого ключа в CI.

## Что подтверждается отдельно

Успешная сборка и проверка подписи подтверждают пригодность файла к передаче тестировщику. Реальное обновление на конкретном телефоне, сохранность его данных и работа VPN проверяются на устройстве. Первая версия с механизмом обновления может показать «Установлена последняя версия»; полный сценарий обновления проверяется при публикации следующего выпуска с большим номером сборки.
