# IPv6 и скорость передачи данных в Pushok

Подготовлено 28 ноября 2026 года. Это технический план и критерии приёмки;
он не подтверждает изменения VPS или измеренный прирост скорости.

## Проверенная отправная точка

- Flow: публичная 2.0.11, сборка 76; исходная ветка подготовки основана на
  `1949ac2256331f539ef727d3bcc56d10984d2f4a`.
- Shop: публичная 2.028, исходная ветка исправления основана на
  `32ebb4ae7dafd329a7a40b38e435eeb93c8bd37f`.
- В выпускаемом Android-приложении используется WireGuard. Архив Xray/VLESS
  не является подтверждением доступности этих транспортов в текущем APK.
- Shop уже выбирает узел с учётом CPU, нагрузки канала и занятых мест и выдаёт
  заранее подготовленный резерв одной подписки. Повторно представлять это
  как новую функцию IPv6-релиза нельзя.
- Узел fleet имеет один `endpoint_ip`; DNS reconcile управляет одной A либо
  AAAA. Текущий probe проверяет IPv4 DNS/HTTPS. Его healthy не доказывает
  работу IPv6 внутри туннеля или обоих внешних адресов.
- Flow меняет активный узел автоматически только при уже действующей
  системной блокировке трафика вне VPN: GoBackend пересоздаёт TUN. Прямой
  доступ исключённых приложений должен учитываться отдельно. Автоматически
  включать lockdown для всех пользователей нельзя.

## Ближайший кандидат: Flow 2.0.12, сборка 77

1. Проверка интернета выбирает адреса, для которых есть подходящий маршрут
   текущего VPN. Смешанный ответ DNS A+AAAA не делает IPv4-туннель
   непроверяемым из-за одного неподходящего AAAA.
2. TCP-сокет привязан к выбранному VPN Network и конкретному проверенному
   IP. HTTPS сохраняет проверку сертификата и имени, а ответ проверяется
   только пока действительны владелец, сеть и маршруты.
3. Прямой запуск диагностики и фоновая проверка имеют ограниченный срок.
   Завершившаяся смена профиля или Stop инвалидируют старый результат,
   включая результат, уже ожидающий доставки в интерфейс.
4. Пассивный `tools/network_baseline.py` собирает загрузку CPU, steal,
   softirq, счётчики интерфейсов и локальные счётчики ошибок UDP4/UDP6. Он не настраивает
   сервер и не проводит speedtest. Формат и запуск:
   [NETWORK_BASELINE.md](NETWORK_BASELINE.md).
5. Согласованное исправление Shop канонизирует IPv6 из экспорта WGDashboard:
   полная и сжатая записи одного адреса считаются одинаковыми; чужой адрес,
   неверный порт и дубли Endpoint по-прежнему отвергаются.

Это законченный этап исправления диагностики и подготовки измерений.
Он не включает hot-switch IPv4/IPv6, автоматический PMTU, новые DNS-записи
или включение IPv6 на рабочем узле. Проценты ускорения не заявляются.

## Какие изменения могут повысить полезную скорость

| Приоритет | Наблюдение | Изменение после подтверждения |
| --- | --- | --- |
| 1 | Потери/задержки на конкретном пути | Выбор другого здорового узла или семейства адресов с проверкой реального трафика |
| 1 | Мелкие запросы проходят, большая передача зависает | Проверка PMTU, ICMP Packet Too Big и согласованного MTU туннеля |
| 1 | Канал близок к подтверждённому лимиту | Перераспределение новых подключений и увеличение ёмкости узла |
| 2 | Высокий steal, перегрузка ядра/softirq | Проверка размещения VPS и CPU, backend ядра на сервере |
| 2 | Растут RcvbufErrors/SndbufErrors/drops | Исправление конкретной переполняющейся очереди с повторным измерением |
| 2 | Большой RTT именно под нагрузкой | Управление очередью на установленном узком месте, а не безусловное увеличение буферов |
| 3 | Медленно начинается открытие сайта | Проверка доступности/задержки DNS и выбранного CDN-маршрута |

DNS-задержка не равна скорости уже установленной передачи. Низкий ping
не гарантирует большой throughput. Прямые маршруты MAX, VK, банков и других
выбранных приложений сохраняются; их эффективность сравнивается отдельно.

`tcp_congestion_control` выбирает алгоритм локальных TCP-сокетов Linux.
Обычный WireGuard gateway пересылает TCP телефона внутри UDP-туннеля.
Поэтому BBR на этом gateway не заменяет congestion control пересылаемого
TCP телефона. Для HTTPS или TCP-прокси, где сервер завершает TCP, это другой
сценарий и отдельный эксперимент. Универсальный набор sysctl в релиз не входит.

## Следующий этап: два внешних адреса одного узла

### Shop и управление сервером

- Ввести несколько endpoint одного узла с явными family, адресом, портом,
  DNS ownership и состоянием проверки. Миграция создаёт один endpoint из
  текущего поля и сохраняет работающую выдачу v1.
- Для A и AAAA нужны отдельные записи владения и reconciliation. Режим
  DNS only для прямых WireGuard/MTProxy; обычный HTTP proxy Cloudflare
  не используется как UDP-транспорт.
- Проверять отдельно внешний путь IPv4, внешний путь IPv6 и внутренний
  IPv4/IPv6-трафик. Не объявлять адрес исправным по ping, DNS или одному
  факту наличия IPv6 на интерфейсе.
- Согласовать версионирование feed с обоими строгими парсерами. Старым
  клиентам сохранять совместимый v1; дополнительные данные не должны
  превращать обновление в отказ импорта действующей подписки.
- До выдачи клиентских глобальных IPv6 подтвердить у хостинга выделение
  адресов/префикса, обратный маршрут, firewall и forwarding. Один IPv6 VPS
  не подтверждает владение целым /64.

### Flow и выбор пути

- Разрешать имена в контексте нужной физической сети и проверять её
  возможности. Само наличие A+AAAA не является рабочим fallback.
- Для начала соединения пробовать ограниченное число кандидатов.
  Рабочий путь подтверждают handshake и ответ на трафик через туннель.
  Не гонять два endpoint одного peer одновременно без проверки roaming.
- Сохранить единый TUN при смене внешнего endpoint либо использовать
  существующее ограничение по системной защите. Способ горячего изменения
  endpoint должен поддерживаться backend; скрытые API/reflection не подходят.
- Успешный путь хранить в коротком локальном кеше с привязкой к поколению
  сети и узлу. При смене Wi-Fi/мобильной сети переоценивать его. Не записывать
  SSID/BSSID, ключи, subscription URL или список посещений в телеметрию.
- Использовать ограничение попыток и паузу перед повторным переключением.
  Небольшой скачок ping не должен обрывать работающую передачу.
- Успешное соединение по IPv6 не означает, что нужно включить `::/0` внутри
  туннеля. Это отдельная серверная возможность и отдельная проверка маршрутов.

## Этап MTU и измерения качества

Сначала измерить поддерживаемый размер пакета по фактическому пути. MTU
физического интерфейса даёт только верхнюю границу первого участка и не
является PMTU всего пути. Сохранить заданный MTU профиля до появления
подтверждённого основания для изменения; учесть overhead внешнего IPv4/IPv6
и минимальные требования IPv6 внутри туннеля.

Контролируемые пробы должны иметь ограниченный объём и проверку получения.
Один потерянный пакет не доказывает слишком большой MTU. Нужны повторение,
возврат к последнему проверенному размеру и разделение PMTU-проблем,
обычных потерь, недоступного peer и перегруженного узла. Фиксированное
«MTU 1280 всем» либо «1420 всем» не считается адаптивной настройкой.

Выбор узла должен учитывать успешность передачи, свежесть измерений,
задержку под нагрузкой, потери и доступную ёмкость. Пользовательские
данные и содержимое трафика для этого не требуются.

## Матрица приёмки

| Сценарий | Проверяемый результат |
| --- | --- |
| IPv4-only сеть и прежний профиль | Подключение, DNS/HTTPS и крупная передача работают |
| A+AAAA и только IPv4-маршрут внутри VPN | Проверка выбирает подходящий адрес и не уходит в обычную сеть |
| IPv6-only внутренний маршрут | Выбирается подходящий AAAA; A не даёт ложный unknown |
| Оба семейства внутри VPN | Проверяются только допустимые адреса, TLS hostname сохраняется |
| Недоступный IPv6/недоступный IPv4 | Ограниченное ожидание; результат не считается успехом по одному UP |
| Подмена TLS/редирект/ошибочный HTTP-ответ | Проверка не сообщает ok |
| Stop, смена профиля, аккаунта или сети во время проверки | Старый результат отбрасывается, сокеты закрываются |
| Исключённые приложения | Их прямой доступ сохраняется в поддерживаемом режиме Android |
| Выход/истечение доступа | Новый выбор пути не продлевает подписку и не обходит авторизацию |
| Обновление поверх 2.0.11 | Прежний сертификат, аккаунт, профили и настройки сохраняются |

Для оценки производительности нужны один и тот же телефон, сеть, узел и
удалённый сервер. Сравнивать текущий APK и кандидат несколькими чередующимися
повторами: TCP download/upload одним и несколькими потоками, ограниченный
UDP loss/jitter, RTT без нагрузки и под ней, длительная HTTPS-передача,
CPU и нагрев телефона. Сохранять медиану и разброс, а не лучший результат.
Улучшение заявлять только когда оно воспроизводится за пределами разброса.

Сервер iperf3 на самом WG VPS измеряет участок до VPS. Для обычного
пользовательского интернета нужен также независимый тестовый сервер за
шлюзом. `iperf3 -4/-6` выбирает семейство тестового потока; внешний endpoint
WireGuard фиксируется отдельно. Нагрузочные тесты не запускаются автоматически
при открытии приложения или на чужих публичных серверах.

## Выпуск и откат

1. Успешные обязательные проверки точного коммита и универсального APK.
2. Подпись прежним сертификатом, проверка package/version/build/minSdk,
   ABI, SHA-256 и штатного `update.json`.
3. Приёмка изменённой диагностики на Android и проверка отсутствия утечек.
   Для заявления об ускорении дополнительно нужны результаты сравнения.
4. Расширение инфраструктуры начинать с одного тестового узла и проверенной
   AAAA; IPv4 сохранять. Применять миграции с резервной копией и планом
   возврата прежних endpoint/DNS без удаления аккаунтов и подписок.
5. Возврат приложения выполнять исправляющим выпуском с большим versionCode
   и прежней подписью; установка старого APK поверх нового не является
   стандартным откатом Android.
